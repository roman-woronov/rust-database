Key–value storeRust, in memory

Every value in rust-database carries a version number. A transaction keeps its writes to itself, notes the version of each key it reads, and commits only if none of those versions moved.

Storesrc/lib.rs

One map. Every value has a version.

The whole database is a HashMap<String, (u64, String)> behind an Arc<Mutex<…>>. Cloning a Database copies the handle, not the data, so every clone and every transaction works on the same map.

The version is what makes transactions possible. It tells a reader whether a key changed since it last looked, without comparing values.

  • insertA new key is stored at version 1.
  • insertAn existing key gets the new value and its version goes up by 1.
  • deleteThe entry is removed, version included.

Transactionssrc/transaction.rs

Writes wait in a buffer until commit.

1

Stage

set and delete write to the transaction’s own pending map, where a delete is stored as None. get answers from pending first. On a miss it reads the store and records the version it saw in reads.

let mut tnx = db.begin();
tnx.set("k".to_string(), "v".to_string());
let n = tnx.get("counter");
2

Validate

commit compares every key in reads with the store. If a version changed, or a key appeared or disappeared, it returns Err(CommitErr::Conflict) and writes nothing.

if *seen_version != current_version {
    return Err(CommitErr::Conflict);
}
3

Commit

When every read is still current, the pending writes go to the store. Some(v) becomes an insert and None becomes a delete. commit takes self, so a transaction can only be used once.

match value {
    Some(v) => self.db.insert(key, v),
    None => self.db.delete(&key),
}

Rollback is a drop.

A transaction that goes out of scope without commit takes its pending writes with it. The store never saw them. The test drop_without_commit_is_rolled_back checks this.

ConflictWorked example

Two readers, one counter. The second commit fails.

StepTransaction 1Store: counterTransaction 2
t1begin, then get("counter") reads "0" at v1"0" 1
t2"0" 1begin, then get("counter") reads "0" at v1
t3set("counter", "1") is staged"0" 1
t4commit finds v1 unchanged and writes Ok(())"1" 2
t5"1" 2set("counter", "1") is staged
t6"1" 2commit saw v1, store has v2: Err(Conflict)

Without the check, both transactions would write "1" and one increment would be lost.

Keys a transaction only writes are not checked. In two_live_transactions both sides call set without reading, both commits succeed, and the later one wins.

Open issues

  • Concurrency

    Commit is not atomic yet.

    Validation and each write take the lock separately, so another commit can land between the check and the writes.

  • Errors

    No automatic retry.

    A conflict returns an error and the caller has to start a new transaction.

  • Isolation

    Blind writes are not checked.

    A key that a transaction writes without reading cannot cause a conflict, so the last commit wins.

  • Versions

    Delete resets the count.

    A key that is deleted and written again is back at v1, so a transaction that read the old v1 will not notice the change.

  • Durability

    Memory only.

    Nothing is written to disk. The data is gone when the process exits.
