Optimistic transactions for the new millennium

Every value carries a version number. A transaction keeps its writes to itself, remembers the version of every key it reads, and commits only if none of them moved.

The other Y2K bug

In 1999 the fear was a two-digit year rolling over from 99 to 00. rust-database stores every value as (u64, String) behind one Arc<Mutex<HashMap>>, so its version counter will not run out. Its rollover comes from somewhere else.

An insert on a new key stores version 1. An insert on an existing key replaces the value and adds 1. A delete removes the entry, and the version goes with it.

So a key that is deleted and written again starts over at v1. A transaction that read the old v1 sees v1 again at commit time and cannot tell that the value changed in between.

The counter itself is safe: a u64 tops out at 18,446,744,073,709,551,615. At a million writes per second to one key, that takes about 585,000 years.

Version-o-matic 2000key "k"
insert("k", "c") VAL "c" v01 ROLLOVER: back to v01

src/transaction.rs

Three moves to commit

A transaction does not touch the store until it commits. It keeps two private maps: pending for its own writes and reads for the versions it saw.

1

Stage

set and delete write to pending, where a delete is stored as None. get answers from pending first. On a miss it reads the store and records the version it saw.

let mut tnx = db.begin();
tnx.set("k".to_string(), "v".to_string());
let n = tnx.get("counter");
2

Validate

commit compares every key in reads with the store. If a version changed, or a key appeared or disappeared, it returns Err(CommitErr::Conflict) and writes nothing.

if *seen_version != current_version {
    return Err(CommitErr::Conflict);
}
3

Commit

When every read is still current, the pending writes go to the store. Some(v) becomes an insert and None becomes a delete. commit takes self, so a transaction is used once.

match value {
    Some(v) => self.db.insert(key, v),
    None => self.db.delete(&key),
}
Drop = rollback

A transaction that goes out of scope without commit takes its pending writes with it. The store never saw them. drop_without_commit_is_rolled_back checks this.

Without the version check, both commits would write "1" and one increment would be lost. Keys a transaction only writes are not checked. In two_live_transactions both sides call set without reading, both commits succeed, and the later one wins.

KNOWN ISSUES, rust-database 0.1.0

1. Commit is not atomic yet.
   Validation and each write take the lock separately, so another commit can land between the check and the writes. This is why threaded_increment_race is ignored.

2. No automatic retry.
   A conflict returns an error. The caller has to start a new transaction.

3. Blind writes are not checked.
   A key that a transaction writes without reading cannot cause a conflict, so the last commit wins.

4. Delete resets the version.
   See "The other Y2K bug" above.

5. Memory only.
   Nothing is written to disk.

6. Private to the crate.
   Database is not pub, so other crates cannot use it yet.
